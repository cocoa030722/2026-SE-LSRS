## 1. 프로젝트 개요

### 1.1 시스템 목적

본 시스템은 대학 도서관의 좌석 예약을 전산화하여 학생들이 모바일·웹 환경에서 실시간으로 좌석을 조회하고 예약할 수 있도록 한다. 관리자는 예약 현황을 실시간 모니터링하고, 노쇼 패널티·시험 기간 정책 등을 유연하게 운영할 수 있다.

### 1.2 시스템 범위 (MVP 기준)

> MVP 전략: 하드웨어(IoT 센서, 카메라) 및 AI 기반 예측 기능을 제외하고, 순수 소프트웨어 로직으로 구현 가능한 기능에 집중한다.
>
> 이를 통해 개발 부담을 약 70% 축소하고, 소프트웨어 공학적 설계와 데이터 흐름 제어에 집중한다.

| 기능 구분 | 초기 제안 (Full Scope) | MVP 범위 (Scaled) |
|---|---|---|
| 점유 확인 | IoT 센서 및 카메라 | 웹 QR 체크인 (SW 방식) |
| 회원 관리 | 미정의 | 학생/관리자 회원가입 필수 |
| 수요 대응 | AI 기반 자동 예측 | 관리자 수동 정책 설정 |
| 복잡도 | 매우 높음 (HW 필요) | 보통 (SW 로직 집중) |

### 1.3 개발 로드맵 (2-Sprint)

| 스프린트 | 주요 목표 | 산출물 |
|---|---|---|
| Sprint 1: Core | 핵심 기능 구현 | 회원가입·로그인, 실시간 좌석 조회·예약, 기본 DB 스키마 |
| Sprint 2: Quality | 운영 품질 강화 | QR 체크인, 노쇼 패널티, 관리자 대시보드, UI/UX 고도화 |

## 4. 비기능 요구사항

### 4.1 유지보수성 (Maintainability)

예약 정책(노쇼 기준 횟수, 체크인 제한 시간, 이용 제한 기간 등)이 변경될 수 있으므로, 정책 값은 코드에 하드코딩하지 않고 설정 파일 또는 DB 기반 파라미터로 관리해야 한다.

- 정책 관련 비즈니스 로직은 서비스 레이어에 집중시켜 UI·DB 변경에 독립적으로 수정 가능해야 한다.
- 코드 변경 없이 정책 파라미터만 수정하여 동작이 바뀌어야 한다.

### 4.2 테스트 용이성 (Testability)

예약 규칙(중복 방지, 체크인 시간 검증)과 권한 규칙(학생/관리자 분리)은 단위 테스트로 독립적으로 검증 가능해야 한다.

- 비즈니스 로직과 인프라(DB, 외부 API)의 의존성을 분리하여 Mock 기반 테스트를 지원한다.
- 스케줄러의 자동 취소 로직은 시간 조작이 가능하도록 설계한다.

### 4.3 이해 가능성 (Understandability)

교육용 프로젝트이므로 아키텍처와 코드 구조가 명확하게 계층화되어야 한다.

- Controller → Service → Repository 3 계층 구조를 일관되게 유지한다.

### 4.4 가용성 및 성능 (Availability / Performance)

시험 기간에 좌석 조회 요청이 집중될 수 있으므로 다음을 고려한다.

- 좌석 조회 API 의 응답 시간은 일반 운영 기준 500ms 이내를 목표로 한다.
- 동시 다수 예약 요청 시 DB 레벨의 트랜잭션 잠금으로 좌석 중복 배정을 방지한다.
- 스케줄러는 체크인 미이행 감지를 10 분 주기로 실행한다.

### 4.5 보안 (Security)

- 비밀번호는 BCrypt 알고리즘으로 해시하여 저장한다.
- JWT 토큰은 만료 시간(Access: 1 시간, Refresh: 7 일)을 설정한다. (D)
- 학생은 타 학생의 예약 정보에 접근할 수 없다.
- SQL 인젝션 방지를 위해 파라미터 바인딩(JPA/Prepared Statement)을 사용한다.

## 5. MVP 제외 범위 (향후 확장 고려)

- IoT 센서 및 카메라 기반 실시간 점유 감지

- 외부 학사 시스템 연동 (수강 정보 기반 자동 예약)
